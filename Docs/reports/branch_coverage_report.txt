1. EXECUTIVE SUMMARY & BRANCH METRICS
--------------------------------------------------------------------------------
Branch coverage (also known as Decision Coverage) measures whether every conditional 
branch in the control flow graph (such as 'if', 'elif', 'else', 'while', 'for', and 
boolean logic operators) has been evaluated to both TRUE and FALSE during test suite 
execution.

In safety-critical cyber-physical systems like APMS—where software directly controls 
physical vehicle barrier gates, monetary financial transactions, and atomic hardware 
reservations—high branch coverage is essential to guarantee that no hidden logical 
paths or unhandled edge cases exist.

2. IMPORTANCE OF BRANCH COVERAGE IN APMS
--------------------------------------------------------------------------------
Statement coverage alone can create a false sense of security; a single statement can 
contain multiple logical decision branches that behave differently under edge 
conditions. Branch testing in APMS verifies:

  1. Physical Barrier Gate Safety:
     Ensures barriers NEVER actuate when a payment is unpaid, partial, or expired, 
     verifying both the 'open' and 'locked' branch outcomes.
  2. Financial & Tariff Correctness:
     Verifies exact monetary transitions at boundary minutes (e.g., minute 10 vs 
     minute 11 for grace periods; minute 600 for daily cap saturation).
  3. Race Condition Prevention:
     Verifies atomic conditional updates (status='FREE' vs status='OCCUPIED') under 
     high-speed simultaneous multi-gate arrival threads.
  4. PCI-DSS Compliance & Card Data Leakage:
     Guarantees that branching logic correctly intercepts any 13-to-19 digit card 
     pattern and masks it before persistence or logging occurs.

4.1 Progressive Billing Fee Engine (backend/app/services/billing.py)
  Total Branches: 12 | Partial: 0 | Branch Coverage: 100.0%
  Decision Points Evaluated:
    Branch 1: Grace Period Evaluation (duration <= grace_minutes)
      - TRUE Path : Duration 0 to 10 minutes -> Fee = 0.00 (Customer leaves free).
      - FALSE Path: Duration >= 11 minutes -> Enters progressive calculation.
    Branch 2: Tier 1 Hourly Slab (billable_hours == 1)
      - TRUE Path : First hour billed at first_hour_rate (e.g. INR 30.00).
      - FALSE Path: Evaluates second tier.
    Branch 3: Tier 2 Hourly Slab (billable_hours == 2)
      - TRUE Path : Second hour billed at second_hour_rate (e.g. INR 50.00).
      - FALSE Path: Evaluates third tier.
    Branch 4: Tier 3+ Progressive Additional Slabs (billable_hours > 2)
      - TRUE Path : Additional hours billed progressively at hourly_rate.
    Branch 5: Single-Day Cap Saturation (uncapped_fee >= daily_max)
      - TRUE Path : 10 hours uncapped = 210, clamped to daily_max = 200.
      - FALSE Path: Stays below daily max keep exact calculated total.
    Branch 6: Multi-Day Stay Division (duration > 1440 minutes)
      - TRUE Path : Stays exceeding 24 hours divided into full days and remainder.
      - FALSE Path: Same-day stay handled directly.
  Validation: 74 boundary tests in test_fee_boundary.py guarantee every decision 
  outcome is exercised at and around exact boundary boundaries (+/- 1 minute).

6. TEST DESIGN TECHNIQUES UTILIZED
--------------------------------------------------------------------------------
To achieve high branch decision coverage across complex parking workflows, the 
following formal software engineering test design techniques were utilized:

  1. Boundary Value Analysis (BVA):
     Applied to grace minutes, hourly slabs, and 24-hour daily cap ceilings. 
     Tests evaluated exact boundaries: (V - 1), V, (V + 1).
  2. Equivalence Class Partitioning (ECP):
     Input domains partitioned into valid and invalid classes (e.g., valid plates, 
     syntactically invalid plates, SQLi injection strings, negative duration values).
  3. Condition / Decision Coverage (C/DC):
     Boolean expressions containing compound clauses (e.g., status == PAID AND 
     elapsed <= 15) evaluated to ensure each individual condition independently 
     affects the decision outcome.
  4. Fault Injection & Simulated Failures:
     Gate timeouts, card declines, duplicate plate entries, and database lock 
     contention injected to exercise all error and rollback branches.
