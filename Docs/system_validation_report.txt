3. END-TO-END FUNCTIONAL WORKFLOW VALIDATION
--------------------------------------------------------------------------------

3.1 Vehicle Entry & ANPR Gate Automation (APMS-F-001, APMS-F-002, APMS-F-003)
  Workflow Description:
    A vehicle approaches the physical entry barrier. The ANPR optical camera captures 
    the license plate. The system verifies confidence (>= 0.80), checks facility 
    capacity, queries for active open sessions (preventing duplicate entry), generates 
    a unique parking session ID, assigns the nearest available slot, and actuates 
    the barrier arm.
  Empirical Validation Results:
    - ANPR recognition with >= 0.80 confidence accepted and session created.
    - Fault injection (low confidence < 0.80 or unreadable plate) seamlessly diverted 
      to manual attendant entry terminal without gate deadlock.
    - Attempted entry with an already active session correctly rejected with HTTP 409 
      Conflict ("Vehicle already inside facility").
    - Attempted entry when facility is at 100% capacity rejected with HTTP 400 Bad 
      Request ("Parking lot full").
    - Verification: 25 automated tests across test_entry_plate.py, test_entry_rules.py, 
      test_entry_session.py, and test_kiosk.py.
    - Outcome: PASS.

3.2 Nearest-Distance Greedy Slot Allocation (APMS-F-004)
  Workflow Description:
    Upon entry, the system evaluates available slots compatible with the vehicle type 
    (Standard Car, Two-Wheeler, EV with Charger, Accessible) and allocates the slot 
    minimizing Euclidean distance from the entry gate.
  Empirical Validation Results:
    - Vehicle type matching verified: Two-wheelers routed to Compact/Moto slots; 
      Cars routed to Standard; EVs routed to EV Charging bays.
    - Distance sorting verified: For entry gate G1, slots on Floor 1 Bay A (distance 
      12.5m) prioritized over Floor 2 Bay C (distance 45.2m).
    - Verification: 9 automated tests in test_slots.py.
    - Outcome: PASS.

3.3 Atomic Concurrency & Race Condition Elimination (APMS-F-005)
  Workflow Description:
    High-volume multi-gate arrivals could simultaneously attempt to claim the same 
    nearest slot. The system must guarantee exactly one vehicle secures the slot 
    without double-booking or transaction deadlock.
  Empirical Validation Results:
    - 20 concurrent threads attempting to claim the single remaining slot in Zone A.
    - Evaluated under atomic SQL conditional semantics:
      "UPDATE slots SET status='OCCUPIED' WHERE id=:id AND status='FREE'"
    - Exact result: 1 thread acquired slot (HTTP 200 OK); 19 threads redirected to 
      next nearest slot or returned lot full.
    - Zero double bookings observed across 10,000 simulated allocations.
    - Verification: 17 automated tests in test_concurrency.py and test_slots_atomic.py.
    - Outcome: PASS.

3.4 Real-Time Availability & Live Display Boards (APMS-F-006)
  Workflow Description:
    Occupancy changes must propagate to entrance LED signage and web dashboards within 
    2 seconds using Server-Sent Events (SSE).
  Empirical Validation Results:
    - Entry and exit event triggers immediately published to SSE stream.
    - End-to-end event propagation latency: < 0.08 seconds (exceeding requirement <= 2s).
    - Live breakdown by vehicle type and zone accurately maintained.
    - Verification: 12 automated tests in test_availability.py and test_availability_live.py.
    - Outcome: PASS.

3.5 Exit Identification & Progressive Billing Computation (APMS-F-007, APMS-F-010)
  Workflow Description:
    Vehicle reaches exit barrier. ANPR camera identifies plate, matches active session, 
    calculates elapsed parking duration, applies vehicle-specific tariff slabs, grace 
    period discounts, and daily maximum caps.
  Empirical Validation Results:
    - Short stays within 10-minute grace period billed at exactly INR 0.00.
    - Tiered hourly progression accurately computed (Hour 1: INR 30; Hour 2: INR 50; 
      Hour 3+: INR 20/hr).
    - Daily maximum cap (INR 200/day for Car) enforced at 10 hours and preserved up 
      to 24 hours.
    - Multi-day stays calculated as: (Full Days * Daily Cap) + Slab(Remaining Hours).
    - Boundary cases tested: 0m, 9m, 10m, 11m, 59m, 60m, 61m, 23h59m, 24h00m, 24h01m, 
      48h, 7 days, 30 days.
    - Verification: 95 automated tests in test_billing.py and test_fee_boundary.py.
    - Outcome: PASS.

3.6 Multi-Channel Payment & POS Gateway Simulation (APMS-F-012)
  Workflow Description:
    Supports Cash at attendant kiosk, Chip & PIN / Contactless EMV Card, and UPI QR 
    code via gateway simulator. Handles successful payments, card declines, network 
    timeouts, and automatic retries.
  Empirical Validation Results:
    - CASH payment processed with exact tender and change calculation.
    - CARD payment verified with simulated gateway authorization token.
    - UPI dynamic QR string generated with session ID and exact amount.
    - Gateway failure correctly transitions session to PAYMENT_PENDING with retry option.
    - Gateway timeout recovered via idempotent transaction polling.
    - Verification: 12 automated tests in test_payment.py.
    - Outcome: PASS.

3.7 Legal Tax Receipt Issuance (APMS-F-013)
  Workflow Description:
    Upon payment, system generates an itemized receipt with unique receipt number, 
    entry/exit timestamps, total duration, reverse 18% GST breakdown (CGST 9% + 
    SGST 9%), payment method, and masked card/UPI references.
  Empirical Validation Results:
    - Mathematical verification: Base Amount = Total / 1.18; CGST = Base * 0.09; 
      SGST = Base * 0.09. Rounding sum equals total fee to exact paise.
    - Masking verification: No plaintext card numbers printed on receipts.
    - Verification: 8 automated tests in test_receipt.py.
    - Outcome: PASS.

3.8 Exit Barrier Interlocking & Session Closure (APMS-F-008)
  Workflow Description:
    Barrier actuation engine locks barrier down until payment status is verified as 
    PAID or parking fee is zero (within grace period). Once vehicle departs, session 
    is marked CLOSED and slot is set to FREE.
  Empirical Validation Results:
    - Unpaid sessions strictly denied barrier open (HTTP 402 Payment Required).
    - Paid sessions actuate barrier open within 0.12s.
    - Post-payment departure grace period (15 minutes) enforced: if vehicle fails 
      to depart within 15 minutes, secondary overdue fee is calculated.
    - Verification: 17 automated tests in test_exit_authorise.py and test_exit_payment_api.py.
    - Outcome: PASS.

3.9 Attendant Manual Override & Anti-Corruption Audit Trail (APMS-F-009)
  Workflow Description:
    Authorized parking attendants can manually open barrier arms for VIPs, emergency 
    vehicles, or system failures, provided an explicit reason is logged in an 
    append-only audit table.
  Empirical Validation Results:
    - Override denied without valid Attendant/Admin JWT token (HTTP 401/403).
    - Override rejected if reason string is empty or missing (HTTP 422).
    - Legitimate override immediately lifts barrier and writes immutable entry to 
      audit_log containing user_id, timestamp, gate_id, plate, and reason text.
    - Verification: 11 automated tests in test_override.py.
    - Outcome: PASS.

3.10 Admin Configuration & Reporting Operations (APMS-F-011, APMS-F-014, APMS-F-015)
  Workflow Description:
    Administrators configure dynamic tariffs, manage slots, view occupancy dashboards, 
    and export revenue audit reports in CSV format.
  Empirical Validation Results:
    - Tariffs dynamically updated in database take effect immediately for subsequent 
      parking sessions without requiring service restart.
    - Revenue and occupancy reports correctly aggregate daily, weekly, and monthly totals.
    - CSV export generates valid RFC 4180 tabular data.
    - Verification: 27 automated tests in test_tariffs.py, test_tariff_config.py, 
      and test_dashboard.py.
    - Outcome: PASS.

5. SECURITY ARCHITECTURE & VULNERABILITY VALIDATION
--------------------------------------------------------------------------------

5.1 Transport Layer Security & Protocol Enforcement (APMS-SR-001)
  - All plain HTTP requests automatically redirected to HTTPS (HTTP 301/308).
  - Strict-Transport-Security (HSTS) enforced with max-age=31536000 and includeSubDomains.
  - OWASP Secure Headers validated on all responses:
    * Content-Security-Policy: default-src 'self'
    * X-Frame-Options: DENY (anti-clickjacking)
    * X-Content-Type-Options: nosniff (MIME sniffing prevention)
    * Referrer-Policy: strict-origin-when-cross-origin
  - Verification: 32 tests across test_https.py and test_security_headers.py. Status: PASS.

5.2 Role-Based Access Control & Credential Storage (APMS-SR-002, APMS-SR-003)
  - Password hashes stored using salted bcrypt algorithms (zero plaintext credentials).
  - JWT tokens cryptographically signed with HMAC-SHA256, verifying expiration (exp).
  - Strict separation of duties: Attendants restricted from administrative endpoints 
    (HTTP 403 Forbidden verified on /admin/*).
  - Verification: 25 tests across test_auth.py, test_rbac.py, and test_seed_and_security.py. Status: PASS.

5.3 Immutable Audit Logging (APMS-SR-004)
  - Append-only audit logging table (audit_log) captures all privileged actions.
  - No UPDATE or DELETE API endpoints exposed on audit log tables.
  - Timestamp, actor user ID, target entity, and client IP address logged.
  - Verification: 16 tests in test_audit.py. Status: PASS.

5.4 PCI-DSS Compliant Cardholder Data Protection (APMS-SR-005)
  - Zero Primary Account Numbers (PAN), CVVs, or magnetic stripe data stored anywhere 
    in database tables, log files, or error tracebacks.
  - Card numbers strictly masked before logging or receipt printing (e.g., ****-****-****-4242).
  - Automated compliance inspection sweeps database to guarantee zero unmasked credit 
    card patterns exist.
  - Verification: 9 tests in test_card_security.py. Status: PASS.

5.5 Injection Resistance & Boundary Fuzzing (APMS-SR-006)
  - All database queries executed through SQLAlchemy parameterized statements.
  - SQL injection fuzzing payloads (e.g., "' OR '1'='1", "'; DROP TABLE sessions;--") 
    safely rejected as invalid license plates or literal queries without syntax compromise.
  - Input boundary fuzzing: Unicode characters, script tags (<script>), and oversized 
    strings safely sanitized with HTTP 422 Unprocessable Entity.
  - Verification: 26 tests in test_input_validation.py. Status: PASS.

5.6 Brute-Force Prevention & Account Lockout (APMS-SR-007)
  - 5-strike failed authentication policy implemented.
  - 5 consecutive invalid password attempts automatically lock account for 15 minutes.
  - Timing attacks mitigated by constant-time password comparison routines.
  - Verification: 20 tests in test_session_lockout.py. Status: PASS.
